# 14단계 | 업무 앱 접근 판정 구분

- **수정 파일:** `on-client/student/extension.mjs`
- **수정 함수:** `renderDecision`
- **관련 커밋:** [72b6ce4c](https://github.com/BoatingDuck/choi-bujang-secret-vault/commit/72b6ce4c6eb1a4b1455886616a93f33756f8f9a0)

## 작업 내용

업무 앱에 접근하지 못한 상황이라도 이유는 다를 수 있다. 정책에 따라 접근이 거부된 것인지, 서버 요청 자체가 실패한 것인지 구분하는 화면이 필요했다.

## 수정한 부분

- `renderDecision`에서 요청 전(`idle`), 확인 중(`loading`), 오류(`error`), 정상 응답(`ok`)을 구분했다.
- 접근 판정은 `allow`, `deny`, `challenge`, `unknown` 네 가지로 나눠 표시했다.
- 서버 요청이 실패하면 '접근 거부'가 아니라 '접근 요청 실패'라고 안내했다.
- 요청한 `appId`와 응답의 `data.appId`가 다르면 해당 판정을 사용하지 않도록 했다.
- 응답에 있는 판정 이유(`reason`)와 확인 시각(`checkedAt`)을 함께 보여줬다. 필요한 값이 없으면 확인 불가로 처리했다.
- `allow`가 나와도 실제 업무 앱 로그인까지 성공했다는 뜻은 아니라는 문구를 넣었다.

## 확인한 내용

| 확인 방법 | 내용 | 결과 |
| --- | --- | --- |
| 코드 확인 | 요청 오류와 정책상 거부를 다르게 표시 | 구현 확인 |
| 코드 확인 | 앱 ID가 다른 응답 거절 | 구현 확인 |
| 코드 확인 | `challenge`, `unknown` 별도 표시 | 구현 확인 |
| 추가 확인 필요 | 각 결과를 실제 화면에서 바꿔가며 확인 | 실행 기록 미첨부 |

## 정리

서버가 응답하지 않았다고 해서 접근이 거부된 것은 아니다. 오류와 판정 결과를 구분해야 사용자도 다음에 무엇을 확인할지 판단할 수 있다고 생각했다.
