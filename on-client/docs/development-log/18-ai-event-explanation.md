## 작업 내용

17단계에서는 AI 연결 상태와 사건 설명의 기본 화면을 구분했다. 이번에는 AI가 만든 요약을 단독으로 보여주는 데 그치지 않고, 선택한 보안 기록의 근거와 규칙, 접속·세션·기기 상태를 함께 확인할 수 있도록 `renderExplanation`을 보완했다.

AI 설명은 참고 정보이므로 보안 판단은 기록에 있는 근거와 연동 시스템의 상태를 기준으로 한다. 설명에 근거가 부족하거나 서로 맞지 않을 때는 내용을 보충해 만들어내지 않고 사용할 수 없다고 안내하는 방향으로 구현했다.

## 수정한 부분

### 요청 상태와 오류 처리

- `explanation.status`가 `error`이면 `event`가 `null`이어도 오류를 먼저 보여준다. 안전성을 확인한 오류 코드·메시지와 실패 이유를 표시하고, 보안 기록은 그대로 유지된다고 안내한다.
- 오류가 없는 상태에서 사건을 선택하지 않았다면 보안 기록을 먼저 고르도록 안내한다. 요청 전(`idle`), 요청 중(`loading`), 성공(`ok`), 실패(`error`)를 구분했다.
- 근거·규칙 부족(`ON_AI_INVALID_INPUT`), 근거 불일치나 응답 검증 실패(`ON_AI_INVALID_OUTPUT`)를 구분하고, 조치를 이미 실행했다고 주장하는 설명은 사용할 수 없다고 알린다.
- 민감한 정보가 의심되는 오류 문구는 그대로 표시하지 않으며, 자동 재시도나 유료 AI 호출은 추가하지 않았다.

### 사건과 근거 연결

- 성공 응답에서도 사건 ID, 요약, 근거, 규칙, 조치의 미실행 여부를 확인한 다음에만 `data-student-explanation-event`에 `event.id`를 지정한다.
- `explanation.data.evidenceIds`를 현재 `event.evidence`의 ID와 대조한다. 누락·중복·존재하지 않는 ID가 있으면 설명을 사용하지 않으며, 없는 근거 문장을 만들어 넣지 않는다.
- 검증을 통과한 경우 근거를 `근거 ID — 근거 글`, 규칙을 `규칙 ID — 규칙 글` 형식으로 표시한다.
- 사건 ID와 AI 요약에는 참고용 안내를 붙여 원본 기록과 AI 해석을 구분한다.

### 확인 불가 상태와 조치 제안

- `event.state`의 `access`, `session`, `device` 가운데 값이 `unknown`인 항목을 각각 `접속/세션/기기: 확인 불가(unknown)`으로 표시한다. 이를 정상 또는 안전으로 바꾸지 않는다.
- `proposals`가 있으면 조치 ID, 이유, 관련 근거 ID를 보여주고 '사람 확인이 필요하며 실행되지 않았습니다'라고 명시한다. 실행 버튼은 추가하지 않았다.
- `proposals`가 비어 있고 `supportedActions`도 비어 있으면 연동 시스템에서 지원하는 조치가 없어 제안이 없는 것이 정상이라고 안내한다. 지원 조치가 있는데 제안이 없는 경우에는 별도로 구분한다.
- 다른 기록을 선택하거나 새로고침·실패 상태로 전환할 때 이전 성공 설명이 남지 않도록 매 호출에서 새로운 DOM을 반환한다. 요청 취소와 최신 응답 구분은 기존 제공 UI의 동작을 유지했다.

DOM 출력은 `document.createElement`와 `textContent`를 사용했다. 이번 단계에서 앞 단계의 학생 함수, 제공 서버, `public/app.js`, 인증 설정은 수정하지 않았다.

## 정리

이번 단계에서 중요하게 본 것은 AI 요약의 표현보다 **어떤 기록과 근거에 연결된 설명인지 확인할 수 있어야 한다는 점**이다. 근거 ID를 현재 사건의 원문과 비교하고, 확인 불가 상태와 미실행 조치를 명확하게 표시하도록 했다.

기존 기록·판정 기능은 그대로 두고 학생 함수 하나만 수정했다. 실제 AI 설명 화면에서의 확인은 유료 요청을 반복하지 않도록 미확인으로 남겼으며, 제출한 코드의 공식 판정은 통과했다.
