## 작업 목표

18단계에서 AI의 사건 설명과 조치 제안을 **참고 정보이자 미실행 상태**로 구분했다. 19단계에서는 조치 준비, 사람 확인, 서버 전달, 접수 응답(ACK), 연동 시스템의 실제 효과 관측을 각각 다른 단계로 표시하도록 학생 화면을 구현했다.

특히 서버가 요청을 받았다는 사실만으로 보안 조치가 성공했다고 표시하지 않도록 했다. 실제 조치를 집행하는 제공 화면과 서버 기능은 수정하지 않고, 학생 코드는 전달받은 결과를 해석하여 보여주는 역할만 맡았다.

## 수정한 부분

### 1. 상태별 표시

| 전달받은 `status` | 학생 화면의 의미 |
| --- | --- |
| `idle` | 아직 미실행. 조치 제안만으로 집행되지 않음 |
| `loading` | 조치 준비 또는 연동 시스템 결과 조회 중. 결과 미확인 |
| `prepared` | 준비됨·미실행. 대상·조치·확인 기한을 살피고 별도 사람 확인 필요 |
| `executing` | 서버에 전달 중. 조치 성공·실제 효과 미확인 |
| `pending` | 서버 접수·처리 중. ACK는 실행 성공이나 효과 관측이 아님 |
| `succeeded` | 검증 가능한 실제 효과 관측이 있을 때만 `효과 확인(succeeded)` |
| `denied` | 연동 시스템의 거절. 안내 메시지가 있으면 함께 표시 |
| `failed` | 연동 시스템 처리 실패. 안내 메시지가 있으면 함께 표시 |
| `unknown` | 결과 불명. 성공·효과 없음 어느 쪽으로도 단정하지 않고 결과만 재조회 안내 |
| `expired` | 사람 확인 기한 만료. 현재 조치를 다시 준비하도록 안내 |
| `error` | 요청 처리 오류. 안전한 오류 코드와 메시지 표시 |

`executing`과 `pending`에서 처리 완료나 효과 확인으로 읽힐 표현을 사용하지 않았다. `unknown`에서는 재집행을 유도하지 않고 제공 화면의 **「원천 결과만 재조회」** 기능을 안내했다.

### 2. 효과 확인 조건과 현재 요청 연결

`status === 'succeeded'`이고 `observation.effectApplied === true`인 경우를 효과 확인의 전제로 삼았다. 구현 코드에서는 여기에 영수증 ID(`receipt.receiptId`), 유효한 관측 시각(`observation.observedAt`), 현재 사건·조치·대상과 영수증 간 확인 가능한 값의 불일치 여부까지 살폈다. 이 조건이 맞지 않는 `succeeded`는 효과 확인 대신 결과 불명으로 표시한다.

- `event.id`와 `event.evidence[].id`, `actionId`, `target.id`, `target.generation`을 **전달된 경우에 한해** 표시한다.
- `receipt.requestId`, `receipt.receiptId`, `receipt.version`, `receipt.replayed`를 **전달된 경우에 한해** 표시한다. `replayed`만으로 새로운 집행이나 성공을 추론하지 않는다.
- 영수증의 `eventId`, `actionId`, 대상 ID·세대가 현재 값과 명시적으로 어긋나면 결과 불명으로 안내한다. 대상 결속 검사는 영수증에 해당 정보가 존재할 때만 적용한다.
- 현재 값과 충돌하지 않는 경우 바깥 요소에 `data-student-action-event`, `data-student-action-request` 속성을 지정한다. 표식만으로 성공을 판단하지 않는다.
- 확인 티켓이나 확인 번호는 학생 함수에 전달되지 않으므로 생성하거나 저장하지 않았다.

### 3. 사용자 확인·중복 요청·화면 갱신의 경계

- 조치 준비, **「대상과 조치를 확인했으며 집행합니다」**, 결과 재조회, 화면 취소는 기존 제공 화면의 역할로 남겨두었다.
- 학생 코드에는 조치 버튼, POST 요청, 인증 티켓, 자동 재조회·자동 재집행을 추가하지 않았다. 따라서 학생 화면의 구현을 서버 측 중복 집행 방지 기능의 실증으로 기록하지 않는다.
- `renderAction`을 호출할 때마다 `document.createElement`로 새로운 DOM을 만들고 `textContent`로 출력한다. 이전 사건·요청·결과를 별도의 학생 상태에 보관하지 않는다.
- **「조치 화면 취소」는 이미 서버에 전달된 조치 효과를 되돌리지 않는다**고 명시했다.
- 오류 메시지는 길이와 비밀정보로 보이는 형태를 검사하고, 부적절한 문자열은 안전한 안내로 바꾼다.
- 13~18단계 학생 함수와 `public/app.js`, 제공 서버, 인증·판정 설정은 수정하지 않았다.

## 정리 및 남은 일

이번 단계에서 핵심은 **요청을 접수했다는 사실(ACK)과 실제 보안 효과를 확인했다는 사실을 분리하는 것**이었다. 학생 화면은 현재 받은 근거와 상태만 표시하고, 결과를 알 수 없을 때는 효과가 없다고 가정하여 중복 집행하지 않도록 안내한다.

현재 기록의 `supportedActions`는 빈 배열이므로 실제 조치 준비 버튼이 보이지 않는 것이 정상이다. 실제 원천 집행기와 학생 계정 권한·대상 확인은 이번 학생 코드만으로 해결되지 않으며 **확인 대기(UNV)**로 남는다. 공식 19단계 제출 판정은 통과했다. 다만 실제 집행 연결과 효과 관측은 여전히 확인 대기(UNV) 상태다.
